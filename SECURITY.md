# Безопасность и приватность

Документ описывает, что приложение делает с системой и данными, и какими
проверками это закреплено. Каждое утверждение здесь либо проверяется тестом из
`tests/` или скриптом из `scripts/`, либо указывает на конкретный файл — чтобы
его можно было перепроверить, а не принимать на слово.

Документ сверен с 2.12.0: закрытие замечаний приёмо-сдаточных испытаний по
Linux-сборке, аудита безопасности от 25.09.2026 и повторного аудита
28.09.2026 (три независимых проверяющих + вскрытие опубликованного deb
v2.11.0).

## Коротко

| Вопрос | Ответ |
|--------|-------|
| Ходит ли в сеть | Нет. Единственный внешний адрес — страница релизов на GitHub; она открывается в браузере пользователя и только по его клику |
| Телеметрия, аналитика | Нет. Собственной нет, служебные обращения Chromium выключены явно |
| Обновляет ли себя само | Нет. Автообновления нет вовсе |
| Нужны ли права администратора | Нет (кроме установки deb-пакета, как у любого пакета) |
| Какие данные хранит | Настройки, загруженные пользователем звуки и фон, итог перелимита мероприятия, снимок таймера для восстановления после сбоя, журнал работы |
| Куда пишет | Каталог данных приложения текущего пользователя; отчёт CSV — только в место, выбранное пользователем в диалоге |
| Открыт ли режим разработчика | Нет. В собранном приложении DevTools окон выключены, а ключи отладки Chromium и Node приводят к выходу |

## Работа без сети

Приложение не обращается в сеть ни при запуске, ни в работе.

- Шрифты поставляются файлами в `fonts/` и подключаются локальными
  `@font-face` (`fonts.css`). Внешних CDN нет.
- Служебные обращения Chromium отключены ключами в `electron-main.js`:
  `disable-component-update` и `disable-features=ChromeVariations,OptimizationHints`.
  Без них движок обращался бы к своим сервисам сам, без единой строки кода
  приложения.
- Проверка орфографии выключена явно: `spellcheck: false` у `webPreferences`
  всех четырёх окон и `session.defaultSession.setSpellCheckerEnabled(false)`
  в `whenReady`. На Linux без этого Chromium сам качает словарь Hunspell по
  сети при первом подчёркивании слова — без единой строки кода приложения и
  незаметно для пользователя; на macOS проверку правописания делает
  системный сервис ОС, а не Chromium, и сети для этого не требуется в
  принципе. Отдельно поведение на Windows не измерялось; `spellcheck: false`
  в любом случае выключает саму функцию целиком, независимо от того, откуда
  она берёт словарь на конкретной ОС.
- CSP каждого окна запрещает сетевые запросы из страницы целиком:
  `connect-src 'none'`, внешние источники скриптов, стилей, картинок и звука не
  разрешены (подробнее — «Content Security Policy» ниже).
- Страница релизов (`RELEASES_URL` в `main-control-ipc.js`) открывается через
  `shell.openExternal` по кнопке «Проверить обновления». Адрес — константа в
  главном процессе; канал `open-releases-page` payload не принимает, поэтому
  страница не может попросить открыть произвольный адрес.

Закреплено `tests/release-gates.test.js`: тест падает, если в поставляемом файле
появится адрес `http(s)://` помимо этого, если внешний адрес уйдёт куда-то кроме
`shell.openExternal`, если шрифт начнёт грузиться не из `fonts/`, или если CSP
разрешит внешний источник.

## Обновления

Автообновления нет: `build.publish` равен `null`, зависимостей вида
`electron-updater` в проекте нет. Приложение не проверяет наличие новых версий и
не подменяет собственные файлы. Новая версия устанавливается только обычной
установкой поверх старой.

Проверяется `tests/release-gates.test.js` (включая запрет появления такой
зависимости) и `scripts/verify-packed.js` на собранном `app.asar`.

## Данные и файловая система

Всё ниже лежит в каталоге данных приложения текущего пользователя
(`app.getPath('userData')`; точные пути по ОС — в
[docs/UNINSTALL.md](docs/UNINSTALL.md)).

| Что | Где | Содержимое |
|-----|-----|------------|
| Настройки | `Local Storage/` (localStorage окон, origin `app://timer-widget`) | Цвета, стили, масштабы, позиции окон; загруженные звуки и фон дисплея — `data:`-URL внутри настроек. Копия настроек версий 2.10.0 и раньше остаётся в origin `file://` того же каталога (см. «Своя схема окон») |
| Метка переноса настроек | `storage-migration.json` (`main-storage-migration.js`) | Статус (`done` / `pending` / `gave-up`), число ключей и попыток, время. Ни ключей, ни значений |
| Итог перелимита мероприятия | `event-overrun.json` (`event-overrun-store.js`) | Секунды перелимита, флаг «мероприятие завершено», журнал докладов (время окончания и перелимит, не больше 500 записей). Срока годности нет |
| Снимок для восстановления после сбоя | `last-state.json` (`recovery.js`) | Длительность, остаток, пресет, «идёт ли», время записи. Старше 5 минут отбрасывается; при штатном выходе и в покое стирается |
| Журнал работы | `electron-log`: на macOS `~/Library/Logs/timer-widget/main.log`, на Windows и Linux `<каталог данных>/logs/main.log` | События приложения и консоль окон. Файл до 10 МБ, при переполнении прежний переименовывается в `main.old.log` |

Отчёт о перелимите (CSV) пишется **только** по кнопке «Выгрузить отчёт» и
**только** в файл, который пользователь выбрал в системном диалоге сохранения.

Приложение не читает пользовательские файлы само: звук и изображение
выбираются пользователем в системном диалоге или перетаскиванием в зону сброса
звука панели. Больше ничего с диска не читается.

Кнопка «Сбросить всё» стирает localStorage и кеш
(`session.clearStorageData()` и `clearCache()`). Итог перелимита обнуляет кнопка
«Новое мероприятие» скрытого раздела.

Меры вокруг записи на диск:

- **Атомарная запись** (`atomic-write.js`): `event-overrun.json` и
  `last-state.json` пишутся во временный файл в том же каталоге — эксклюзивно
  (`O_EXCL`: если на месте временного файла заранее подложена символическая
  ссылка, она не будет прочитана как файл) и с правами 0600, только для
  владельца процесса (файл несёт итог перелимита мероприятия — деньги), затем
  `fsync` и `rename` поверх старого. Сбой посреди записи оставляет прежний
  файл, а не обрезанный JSON; временный файл, залежавшийся от прошлого
  аварийного завершения того же процесса, убирается перед новой попыткой.
  Проверка — `tests/atomic-write.test.js`.
- **Упавший рендерер перезагружается не более трёх раз за скользящую минуту
  на окно** (`CONFIG.CRASH_RELOAD_LIMIT`/`CRASH_RELOAD_WINDOW_MS`,
  `main-window-hooks.js`) — дальше окно остаётся как есть, без дальнейших
  попыток, только запись в журнал. Проверка —
  `tests/main-window-hooks-robustness.test.js`.
- **Перетаскивание окна игнорирует нефизически большой скачок координаты**
  (`CONFIG.MAX_MOVE_DELTA`, `main-geometry.js: moveWindowBy`) — ни
  `setBounds`, ни исключение. Проверка —
  `tests/main-geometry-robustness.test.js`.
- **Недоверенный вход при чтении**: оба файла при запуске нормализуются —
  битый JSON, чужие типы, отрицательные числа дают чистое состояние, а не
  падение (`tests/event-overrun-store.test.js`, `tests/recovery.test.js`).
- **CSV без формул** (`event-report.js`, CWE-1236): текстовая ячейка,
  начинающаяся с `=`, `+`, `-`, `@`, их полноширинных двойников, табуляции или
  CR, получает апостроф и кавычки — табличный редактор не выполнит её как
  формулу. Числа не трогаются. Проверка — `tests/event-report.test.js`.
- **Журнал без путей**: при выгрузке в журнал пишется только имя файла, ошибка
  записи — только кодом (`ENOENT`, `EACCES`); отвергнутая навигация — схемой и
  последним сегментом пути; отказ IPC — именем канала и причиной, без payload.
  Полный путь содержит имя учётной записи, а журнал уходит в поддержку.
  Проверка — `tests/electron-main-load.test.js` (SEC-11).

Реестр ключей localStorage — `CONFIG.STORAGE_KEYS` в `constants.js`;
`tests/storage-keys.test.js` сверяет его с кодом в обе стороны.

## Изоляция процессов

Все четыре окна создаются с одинаковыми ограничениями:

- `nodeIntegration: false` — в странице нет доступа к Node.js;
- `contextIsolation: true` — код страницы и мост изолированы;
- `sandbox: true` — рендерер работает в песочнице ОС;
- `devTools` включаются только при одновременном выполнении двух условий: запуск
  с ключом `--dev` И приложение не собрано (`!app.isPackaged`).

Проверяется `tests/release-gates.test.js` (перечисляет ВСЕ конструкторы окна и
требует полный набор ограничений от каждого) и `scripts/verify-packed.js` (те же
проверки на упакованном артефакте).

### Ключи отладки в собранном приложении

DevTools окна — не единственный вход. Ключи Chromium и Electron, снимающие
песочницу, отключающие изоляцию сайтов или подменяющие запуск дочерних
процессов, дают код в любом окне мимо песочницы, CSP и белого списка IPC —
поэтому собранное приложение (`app.isPackaged`), запущенное с любым из них,
выходит с кодом 1 **до создания первого окна** и до регистрации IPC (самое
начало `electron-main.js`, до `require` модулей главного процесса):

`remote-debugging-port`, `remote-debugging-pipe`, `inspect`, `inspect-brk`,
`no-sandbox`, `disable-sandbox`, `disable-gpu-sandbox`,
`disable-setuid-sandbox`, `disable-namespace-sandbox`,
`disable-seccomp-filter-sandbox`, `disable-web-security`,
`disable-site-isolation-trials`, `single-process`, `in-process-gpu`,
`no-zygote`, `renderer-cmd-prefix`, `gpu-launcher`, `utility-cmd-prefix`,
`browser-subprocess-path`, `js-flags`, `allow-file-access-from-files`,
`remote-allow-origins`.

Гард читает `process.argv` — то, с чем реально запущен процесс, — а не
`app.commandLine.hasSwitch()`: Electron сам дописывает
`--allow-file-access-from-files` в итоговую командную строку Chromium ради
фьюза `grantFileProtocolExtraPrivileges` (см. «Фьюзы Electron» ниже), и гард
по итоговой строке выходил бы с кодом 1 на КАЖДОМ старте без единого
пользовательского ключа. Совпадение — по точному имени ключа (не префиксу):
принимаются обе формы, которые понимает Chromium везде, `--name`/`--name=…`
и однодефисная `-name`/`-name=…`, а на Windows — ещё и `/name` (третий
префикс, которого нет на POSIX: там `/` начинает путь, включая
`argv[0]` деб-пакета), и там же имя ключа приводится к нижнему регистру до
сравнения (`--No-Sandbox` там равносилен `no-sandbox`; на POSIX регистр
значащий).

**Ключ `--zygote-cmd-prefix` неустраним на уровне приложения (Linux).**
Zygote-процесс — механизм Chromium для форка песочницы, существующий
только на Linux (на macOS и Windows его нет вовсе, поэтому там ключ
бессмыслен). Ключ обрабатывается движком до того, как выполнится хоть одна
строка JS главного процесса — гард увидеть его не может в принципе, ни
этот, ни любой другой. Защита от него — не код, а окружение:
непривилегированный локальный пользователь, у которого нет причин
передавать этот ключ приложению самому себе.

В разработке (`!app.isPackaged`) ключи разрешены: через
`--remote-debugging-port` к приложению подключается Playwright, а
несобранный запуск не обязан быть таким же строгим, как то, что уходит
пользователю. По той же границе `!app.isPackaged` гейтятся тестовый режим и
режим съёмки — собранное приложение игнорирует `--screenshot` и
`NODE_TEST_CONTEXT`.

Проверка — `tests/electron-main-load.test.js` (SEC-04).

### Фьюзы Electron

Фьюзы — биты внутри бинаря Electron, которые переворачиваются при сборке
(`build.electronFuses` в `package.json`) и не меняются ни ключом, ни
переменной окружения.

| Фьюз | В сборке | Что это даёт |
|------|----------|--------------|
| `RunAsNode` | выключен | `ELECTRON_RUN_AS_NODE` не превращает приложение в интерпретатор Node |
| `EnableNodeOptionsEnvironmentVariable` | выключен | `NODE_OPTIONS` игнорируется |
| `EnableNodeCliInspectArguments` | выключен | `--inspect*` игнорируются |
| `EnableEmbeddedAsarIntegrityValidation` | включён (проверяется на macOS и Windows) | `app.asar` сверяется с хешем, вшитым при сборке; подменённый архив не запускается |
| `OnlyLoadAppFromAsar` | включён | приложение грузится только из `app.asar`, не из соседнего каталога `app/` |
| `EnableCookieEncryption` | включён | cookie на диске шифруются ключом ОС |
| `LoadBrowserProcessSpecificV8Snapshot` | выключен (как по умолчанию) | — |
| `GrantFileProtocolExtraPrivileges` | **включён — ещё два минорных релиза после выпустившего перенос, выключается в третьем** | окнам не нужен (они на `app://`), нужен переносу настроек из `file://`; см. «Своя схема окон» и «Известные ограничения» |

`resetAdHocDarwinSignature: true`: сборка macOS не подписана, а перевёрнутые
биты ломают штатную ad-hoc подпись Electron — без её пересоздания arm64 macOS
бинарь убивает.

**`EnableEmbeddedAsarIntegrityValidation` проверяется движком только на macOS
и Windows** (документированная граница поддержки Electron — раздел «Version
support» его доки по asar integrity); на Linux фьюз выставлен, но engine его
не читает вовсе, подменённый `app.asar` там запустится. Защита на Linux — не
фьюз, а сам deb: файлы `/opt/TimerWidget` принадлежат root, обычный
пользователь не может их изменить (и потому не может подменить `app.asar`
без sudo) — исключение, `chrome-sandbox`, может стоять `4755` в SUID-режиме
песочницы, но это не право на запись, а бит запуска от имени владельца.
`dpkg --verify timer-widget` сверяет md5sums пакета с тем, что лежит на
диске, и печатает расхождение, если файл всё же тронули.

Биты читаются обратно из собранного бинаря в `scripts/verify-packed.js` (через
`@electron/fuses`) — задание `pack` в CI падает поимённо, если какой-то фьюз не
перевёрнут. Конфиг сторожит `tests/release-gates.test.js`, читалку —
`tests/verify-packed.test.js`.

### Навигация и сброс файлов

- Окно может перейти **только на одну из четырёх своих страниц** схемы
  `app://timer-widget/` (`navigation-guard.js`): `will-navigate`,
  `will-redirect` и `will-frame-navigate` на любой другой адрес — включая
  любой `file://`, даже файл из каталога приложения, — отменяются. Адрес
  сравнивается нормализованным, поэтому `..`, `%2e%2e` и двойные слэши не
  обходят проверку. `window.open` и `<webview>` запрещены
  всегда. Запреты ставятся и в функциях создания окон, и на любой
  `webContents` через `app.on('web-contents-created')`.
- Файл, перетащенный на виджет, часы или дисплей, не открывается вместо окна
  (`drop-guard.js`); у панели свой гаситель (`custom-sounds.js`), который
  пропускает только зону сброса звука.

Без этого HTML-файл, перетащенный на виджет, становился страницей окна — с
мостом IPC и правом `file://` читать диск. Проверки —
`tests/navigation-guard.test.js`, `tests/drop-guard.test.js`.

### Своя схема окон (SEC-12)

После 2.10.0 окна грузятся не с `file://`, а со своей схемы
`app://timer-widget/<страница>` (`app-scheme.js`, `main-app-protocol.js`).

- Схема регистрируется до `ready` с привилегиями `standard` и `secure` — и
  только ими: `supportFetchAPI`, `corsEnabled`, `stream` не даны (окнам
  запрещён `connect-src`, звуки — осцилляторы и `data:`-URL).
- Обработчик (`protocol.handle`) отдаёт **список**, а не каталог: четыре
  страницы окон, страницу переноса настроек, файлы, которые эти страницы
  подключают (`<script src>`, `<link href>` — список собирается из самой
  разметки), и плоские файлы `fonts/` и `sounds/` с их расширениями. Главный
  процесс, `preload.js`, `package.json` не отдаются.
- Отвергается: другой хост, порт, учётка в адресе; `..`, `%2e%2e`, `%2f`,
  `%5c`, обратные слэши, `:`, NUL, двойное кодирование — всё, что после
  одного декодирования не является плоским именем `[A-Za-z0-9._-]`. Чужой
  хост — 403, остальное — 404; отказ — строкой в журнал без полного пути.
- С каждым ответом — `Content-Type` по расширению и
  `X-Content-Type-Options: nosniff`; со страницей — `Content-Security-Policy`
  заголовком: тот же текст, что в `<meta>`, плюс `frame-ancestors 'none'` —
  meta эту директиву не выражает (см. «Content Security Policy» ниже).
- Проверка отправителя IPC и навигация считают своей только страницу этой
  схемы: окно, оказавшееся на `file://`, для них чужое.

**Перенос настроек.** localStorage привязан к origin, и у `app://` он новый и
пустой. При первом запуске новой версии, до первого окна,
`main-storage-migration.js` открывает скрытое окно без preload (нет моста —
нет IPC; `devTools: false`), читает все ключи старого origin `file://`
(`executeJavaScript` — нового канала IPC нет), пишет в `app://` только
отсутствующие там ключи, сбрасывает хранилище на диск и лишь затем ставит
метку `storage-migration.json`. Сбой, таймаут шага (15 с) или квота — метки
нет, повтор при следующем запуске; после трёх неудач — `gave-up`. Новый
профиль (каталога `Local Storage` не было на старте) окна не открывает вовсе.
Сброс на диск Chromium не дождаться, поэтому второй запуск один раз сверяет:
метка «перенесено», а `app://` пуст — перенос повторяется; ключи на месте —
метка помечается `verified`, дальше сверки нет. Повтор после ПРОВАЛИВШЕЙСЯ
попытки (метка `pending`) отдаёт победу значениям из `file://`: окна той сессии
открылись на пустом `app://` и записали туда свои умолчания, и правило «не
трогать существующее» сделало бы их вечными. Цена — правка, сделанная в той же
неудачной сессии, уступит старому значению. «Сбросить всё» ставит метку
«перенесено и сверено», чтобы сверка не вернула сброшенное. Старое хранилище не стирается — откат на прошлую версию найдёт его. В журнал
идут только число ключей и объём.

**Почему фьюз ещё включён.** Прочитать origin `file://` можно только с
включённым `GrantFileProtocolExtraPrivileges`: без него `localStorage` там
бросает «Access is denied for this document». Разбор leveldb Chromium из
главного процесса без нативных зависимостей (журнал, SST, snappy) отвергнут
как хрупкий: его ошибка — тихо потерянные настройки. Поэтому перенос
держится ещё минимум два минорных релиза после того, где он вышел, а в
третьем удаляется в одном коммите с выключением фьюза; пару
«перенос есть ⇔ фьюз включён» держит храповик в
`tests/release-gates.test.js`.

Проверки — `tests/app-scheme.test.js`, `tests/main-app-protocol.test.js`,
`tests/main-storage-migration.test.js`, `e2e/app-scheme.spec.js`,
`e2e/storage-migration.spec.js` (посев `file://` настоящим Electron),
`scripts/verify-packed.js` (окна на схеме в `app.asar`).

### Content Security Policy

Политика четырёх окон — одна строка `CONTENT_SECURITY_POLICY` в `app-scheme.js`
(`scripts/csp-guard.js` сверяет и переписывает по ней meta). Она лежит в
`<meta http-equiv="Content-Security-Policy">` каждого HTML и после 2.10.0 приходит
ещё и заголовком ответа схемы `app://`:

```
default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:;
media-src 'self' data:; font-src 'self' data:; connect-src 'none';
object-src 'none'; base-uri 'none'; form-action 'none'; frame-src 'none';
worker-src 'none'
```

Заголовок ответа схемы `app://` несёт ту же строку с одной добавкой —
`frame-ancestors 'none'` (запрет встраивать окно в чужой `<iframe>`): эту
директиву спецификация CSP запрещает браузеру читать из `<meta>`, поэтому в
`<meta>` её нет и не может быть, а в заголовке она есть (`app-scheme.js`,
`RESPONSE_CONTENT_SECURITY_POLICY`).

- `script-src 'self'` — исполняются только файлы приложения: ни
  `'unsafe-inline'`, ни хешей, ни `'unsafe-eval'`. Внедрённый в страницу
  скрипт (или обработчик `on*=`) не исполнится;
- `style-src 'self'` — применяются только таблицы-файлы: внедрённый `<style>`
  или атрибут `style="…"` не применится. Изменение стиля скриптом через CSSOM
  (`el.style.x = …`) политика не ограничивает — так окна и показывают/прячут
  элементы;
- `connect-src`, `object-src`, `base-uri`, `form-action`, `frame-src`,
  `worker-src` — `'none'`;
- `img-src`, `media-src`, `font-src` — `'self' data:` (фон и звуки
  пользователя живут `data:`-URL).

До 25.09.2026 инлайновые скрипты окон разрешались поимённо (sha256 каждого
блока), а стили — целиком (`style-src 'unsafe-inline'`). Теперь инлайна в окнах
нет: код страниц — `*-app.js`, `*-theme-sync.js`, `theme-init*.js`, стили —
`control.css`, `widget.css`, `clock-widget.css`, `display.css`.

Проверки:
- `npm run csp:check` / `tests/csp-guard.test.js` — в разметке окон нет
  `<script>` без `src`, `<style>`, `style=`, `on*=`, `javascript:`; в их
  скриптах — шаблонов со `style=`/`on*=`, `setAttribute('style')`,
  `createElement('style')`, `eval`; meta совпадает с политикой из
  `app-scheme.js`. Сканер проверен на себе;
- `e2e/csp-strict.spec.js` — ноль событий `securitypolicyviolation` во всех
  четырёх живых окнах при проходе по стилям, ящику и вкладкам;
- `e2e/windows-load-clean.spec.js` — внедрённые `<script>` и `<style>` не
  срабатывают.

### Отказ в разрешениях

Приложение — офлайн-таймер и ни одно из окон не запрашивает разрешений сам,
но запрос может прийти встроенным API Chromium (например, если внедрённый
код всё же попробует). Все обработчики стоят в `whenReady`
(`main-lifecycle.js`), как страховка сверх песочницы/CSP/навигации:

- `setPermissionRequestHandler` и `setPermissionCheckHandler` отказывают
  любому запросу (камера, микрофон, геолокация, уведомления и так далее) —
  безусловно, без белого списка разрешённых;
- `setDevicePermissionHandler` отдельно отказывает запросам устройств
  (WebHID, WebUSB, WebSerial, Bluetooth) — они идут отдельным API мимо
  обычного потока разрешений, и первый обработчик их не видит;
- `setDisplayMediaRequestHandler` отказывает захвату экрана
  (`getDisplayMedia`) — отдаёт пустой список источников, чтобы страница
  получила отказ сразу, а не подвешенный промис.

Проверка — `tests/main-lifecycle-hardening.test.js`.

### IPC

Обмен между страницей и главным процессом идёт через `preload.js` с **белым
списком каналов своего окна**, раздельным для отправки и приёма. Канала «на
всё» нет; неизвестный или чужой для окна канал отбрасывается ещё в мосте. Мост
не даёт `invoke`.

Списки по окнам собираются из одного источника — таблиц `SENDERS` (кто шлёт) и
`RECEIVERS` (кто слушает) в `ipc-senders.js`; генератор
`scripts/preload-channels.js` вписывает их в `preload.js` (песочница не даёт
мосту читать локальные файлы). Окно выбирает свою строку по роли
`--tw-window=<роль>`, которую главный процесс передаёт аргументом рендерера
(`webPreferences.additionalArguments`) до загрузки страницы; без роли, с
неизвестной или с двумя ролями мост закрыт целиком. Так виджет не может даже
поставить в очередь `reset-and-relaunch`, а панель не подписана на геометрию
чужих окон.

Мост — второй слой. Главный процесс по-прежнему проверяет **отправителя**
каждого сообщения
(`ipc-senders.js`): одна таблица «канал → окна, которым его разрешено слать»,
и каждый обработчик регистрируется через обёртку, которая перед вызовом
проверяет, что сообщение пришло из главного кадра одного из четырёх окон, что
адрес кадра — своя страница и что это окно есть в строке канала. Необратимое
(`reset-and-relaunch`, `quit-app`, `event-reset`, `event-finish`,
`event-export`) разрешено только панели. Канал без строки в таблице роняет
загрузку главного процесса — забытое разрешение видно на первом же прогоне
тестов.

Каналы-ретрансляторы (цвета окон, стиль виджета, настройки дисплея и часов)
запоминают payload и досылают его каждому открывающемуся окну, поэтому payload
проверяется до запоминания (`relay-payload.js`): только плоский объект
примитивов, не больше 200 ключей, `__proto__`/`constructor`/`prototype` не
присваиваются, потолок размера — 64 КБ, у настроек дисплея — под фон 10 МБ в
base64. Сверх потолка payload отвергается целиком, а не обрезается.

Числовые параметры команд таймера, размера, позиции и прозрачности
проверяются на конечность и границы (таймер — целые секунды до 99:59:59).

Проверки — `tests/preload-channels.test.js`, `tests/channel-validator.test.js`, `tests/ipc-senders.test.js`,
`tests/relay-payload.test.js`, `tests/ipc-liveness.test.js`,
`tests/electron-main-load.test.js`.

### electron-log

`log.initialize({ preload: false })`: без этого electron-log добавляет в каждую
сессию второй preload с `window.__electronLog` и собственным каналом в обход

## Проверка входных данных

- Изображения: ограничение размера (10 МБ), проверка MIME-типа и **сигнатуры
  файла** (для WebP — `RIFF`/`WEBP`). SVG исключён намеренно: это вектор
  исполнения скрипта.
- Аудио: ограничение 5 МБ, MIME и сигнатура; файл с пустым типом отклоняется;
  в `Audio` попадает только `data:audio/`.
- Значения цветов проверяются одним валидатором (`isSafeColor`) перед
  подстановкой в CSS. Пользовательский текст экранируется (`escapeHTML`).
- Ручной ввод времени разбирается строго (`parseManualTime`): всё, что не
  совпало с форматом, отвергается, а не складывается из обрывков.

См. `security.js`, `utils.js` и тесты `tests/security.test.js`,
`tests/security-extended.test.js`, `tests/color-validation-single-owner.test.js`,
`tests/time-utils.test.js`.

## Песочница в Linux

Для Linux поставляется **только deb**. Ключа `--no-sandbox` нет ни в одной цели
сборки: песочница Chromium либо работает, либо приложение не стартует. AppImage
снят с поставки: шага установки у него нет, поднять песочницу там нечем, кроме
этого ключа, — и именно Linux-сборка с ним не прошла приёмо-сдаточные испытания.

Песочнице нужен один из двух механизмов. Скрипт установки deb
(`build/linux-after-install.sh`) выбирает так:

- **user namespaces** — основной путь. С Ubuntu 24.04 AppArmor ограничивает их
  для приложений без профиля, поэтому пакет ставит профиль с `userns,` в
  `/etc/apparmor.d/` (только если местный AppArmor этот профиль понимает);
- **SUID-root на `chrome-sandbox`** (`chmod 4755`, владелец root) — только там,
  где ядро закрывает user namespaces обычным пользователям: нет самого
  механизма, `kernel.unprivileged_userns_clone=0` (Debian),
  `user.max_user_namespaces=0` или ограничение AppArmor без профиля. Решают
  настройки ядра, а не проба `unshare` — postinst идёт от root, а root
  проходит пробу и там, где пользователю запрещено. В остальных случаях помощник
  остаётся `0755`: лишний SUID-бинарник — сам по себе поверхность атаки.

При удалении пакета профиль AppArmor выгружается и удаляется
(`build/linux-post-remove.sh`). Домашние каталоги пакет не трогает и на
`purge`: скрипт от root не ходит по путям, которыми владеют пользователи;
настройки убираются руками — [docs/UNINSTALL.md](docs/UNINSTALL.md#linux-deb).

Проверяется `tests/release-gates.test.js` и, на собранном пакете,
`scripts/verify-linux-sandbox.js` — в CI и в релизе, на том самом deb, что
уходит пользователям.

**Смена режима песочницы после апгрейда ОС** (например, 22.04 → 24.04, где
меняется доступность user namespaces под AppArmor) требует переисполнить тот
же выбор, а не разбираться руками: `sudo apt install --reinstall timer-widget`
повторно прогоняет `postinst`, который выбирает между user namespaces и
SUID-помощником по текущему ядру и AppArmor — тем же путём, что при первой
установке.

## Версия Chromium и политика обновления

Версия Electron — прямая зависимость (`package.json`), а Chromium внутри неё
отдельно не выбирается: он идёт тем, который зашит в конкретный релиз
Electron. На момент этого документа: Electron 44.4.5 содержит Chromium
152.0.7977.130, тогда как отдельно устанавливаемый Chrome стабильного канала
— 153; Electron 44.4.5 — последний патч-релиз своей линии (44.x).

**Политика.** Проект обновляется на каждый новый патч-релиз Electron внутри
поддерживаемой линии: команда Electron сама подтягивает исправления
безопасности Chromium в патч-релизы (backport), поэтому «последний патч
своей линии» — это и есть актуальный Chromium этой линии, а не отставание.
Отставание от последнего патча — повод обновиться, а не сам факт, что версия
Chromium не совпадает с версией отдельного Chrome (совпадения по номеру и не
предполагается: у Electron и Chrome разные графики релизов).

Сверка автоматическая: `scripts/security-gate.js electron` сравнивает
Electron из lockfile, из SBOM и строку `Electron/X.Y.Z` в собранном бинаре с
последним патчем линии — расхождение в релизе валит сборку.

**Почему бинарный сканер уязвимостей здесь не источник истины.** Скан
собранного deb (Grype по SBOM распакованного `app.asar` + бинаря) видит
Chromium только по строке версии внутри бинаря, если её сопоставит со своей
базой CPE — а сопоставление `Chrome/152` с `cpe:*:google:chrome` даёт
находки, которые к Electron не относятся: то, что уязвимо в отдельно стоящем
Chrome 152, может быть давно закрыто патчем внутри Electron 44.4.5 (или
никогда не быть достижимо — Electron не собирает Chrome целиком, часть
поверхности у него отсутствует). Здесь фиксируется факт несовпадения нумерации,
без утверждений о конкретных CVE: список закрытых Chromium-уязвимостей ведёт
сама команда Electron в примечаниях к релизу.

## Как проверить самостоятельно

CI делает всё это сам на каждом прогоне, а релиз — до сборки артефактов
(подробно — [docs/ci.md](docs/ci.md)):

- **уязвимости**: `npm audit --audit-level=high` и OSV-Scanner по
  `package-lock.json` и `sbom.json`; Grype по SBOM, построенному из
  распакованного deb и `app.asar`. High и critical валят сборку, dev-зависимости
  включены. Принятые находки — только в `osv-scanner.toml` / `.grype.yaml` с
  причиной и сроком; сейчас их нет;
- **Electron/Chromium**: Chromium внутри бинаря сканеры не опознают, поэтому
  версия Electron сверяется трижды — lockfile, SBOM и строка `Electron/X.Y.Z` в
  собранном бинаре — и сравнивается с последним патчем своей линии: в релизе
  отставание — провал (CVE Chromium закрываются патч-релизами Electron);
- **SBOM**: `sbom.json`, прикладываемый к релизу, совпадает с lockfile;
- **песочница на живой системе**: deb ставится на Ubuntu 24.04 (ядро раннера с
  AppArmor) и в чистые ubuntu:24.04, ubuntu:22.04, debian:12; приложение
  запускается обычным пользователем без `--no-sandbox` и обязано прожить 15 с
  после готовности, а его рендереры — работать под seccomp-bpf в своём
  namespace. Проверяются оба пути: user namespaces через профиль AppArmor и
  SUID-помощник. После удаления пакета профиль выгружен из ядра.

Вручную:

```sh
npm audit --audit-level=high   # уязвимости зависимостей (весь граф, как в CI)
npm audit --omit=dev           # то, что попадает в приложение
node scripts/security-gate.js sbom-sync   # sbom.json совпадает с lockfile
node scripts/security-gate.js electron    # Electron: lockfile = SBOM, последний патч
cp sbom.json sbom.cdx.json && osv-scanner -L package-lock.json -L sbom.cdx.json
npm run ci                     # lint + unit-тесты, включая release-gates
npm run csp:check              # CSP окон: политика в meta, ни одного инлайна

npx electron-builder --dir     # собрать без установщика
node scripts/verify-packed.js  # содержимое app.asar, релизные гейты, фьюзы

# фьюзы собранного бинаря (путь зависит от ОС и архитектуры):
npx @electron/fuses read --app dist/mac-arm64/TimerWidget.app
npx @electron/fuses read --app dist/win-unpacked/TimerWidget.exe

# Linux, на машине с dpkg-deb:
npx electron-builder --linux deb
node scripts/verify-linux-sandbox.js
# установить и запустить в песочнице (от root; запуск — от APP_USER):
sudo apt-get install -y ./dist/TimerWidget-*.deb xvfb
sudo APP_USER="$USER" bash scripts/linux-launch-check.sh --expect userns   # или suid
```

## Известные ограничения

1. **Сборки не подписаны.** Сертификата разработчика у проекта нет:
   `mac.identity` равен `null`, подпись Windows отключена. На macOS скачанное
   приложение запускается только после явного разрешения в «Конфиденциальность
   и безопасность»; на Windows SmartScreen предупреждает о неизвестном
   издателе. Подлинность файла проверяется по `SHA256SUMS.txt` рядом с
   загрузками. Когда сертификаты появятся, подпись включается настройками
   сборки без изменений в коде.
2. **`GrantFileProtocolExtraPrivileges` включён, пока жив перенос настроек.** Окна
   после 2.10.0 живут на `app://` и фьюзу ничем не обязаны; обязан ему
   перенос настроек из origin `file://` (без фьюза `localStorage` там бросает
   «Access is denied for this document», замерено 25.09.2026). Решено
   26.09.2026: перенос держится ещё минимум два минорных релиза после
   выпустившего его; в третьем перенос удаляется, фьюз выключается (выйдет в
   2.11 — живёт в 2.12 и 2.13, выключение в 2.14). Цена: пользователь,
   перепрыгнувший через все три релиза, настроек не получит. Пока фьюз
   включён, риск закрыт тем, что ни одна страница приложения на `file://` не
   живёт: навигация на `file://` отменяется, проверка отправителя IPC
   `file://` не принимает, у окна переноса нет моста.
3. **Девятый фьюз провода неизвестен `@electron/fuses` 1.8.0.** Провод Electron
   44 содержит бит с индексом 8, которому в библиотеке нет имени:
   `npx @electron/fuses read` печатает его как `undefined is Enabled`. Сборка
   его не трогает — он остаётся в значении Electron по умолчанию, и
   `verify-packed.js` его не проверяет.
4. **Ручная проверка установщика Windows** (вопрос об удалении настроек при
   деинсталляции) не автоматизирована.
5. **Целостность `app.asar` не проверяется на Linux.** Фьюз
   `EnableEmbeddedAsarIntegrityValidation` там выставлен, но движком не
   читается (граница поддержки самого Electron). Вместо него на Linux
   защищает deb: файлы `/opt/TimerWidget` принадлежат root, обычный
   пользователь не может их подменить без sudo, а расхождение с пакетом
   находит `dpkg --verify timer-widget`.
6. **`--zygote-cmd-prefix` приложение отказать не может (Linux).** Zygote —
   механизм Chromium только для Linux (на macOS и Windows его нет, ключ там
   ничего не значит). Ключ обрабатывает сам движок раньше, чем выполнится
   первая строка JS главного процесса, — гарду ловить нечего в принципе.
   Защита здесь не техническая, а организационная: ключ может передать
   только тот, у кого уже есть доступ локально запускать процессы этого
   пользователя, а такому пользователю не нужен именно этот ключ, чтобы
   навредить — у него и без него есть всё необходимое.

## Как сообщить об уязвимости

Через приватный отчёт о уязвимости в разделе Security репозитория на GitHub
(вкладка Security → Report a vulnerability). Пожалуйста, не открывайте публичную
задачу до исправления.

Что помогает разобраться быстрее: версия приложения, операционная система, шаги
воспроизведения, ожидаемое и фактическое поведение. Журнал приложения
(`main.log`, см. «Данные и файловая система») полных путей к файлам отчётов не
пишет, но пробежать его глазами перед отправкой всё равно стоит.
