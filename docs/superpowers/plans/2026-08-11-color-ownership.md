# План: перевод цвета на каскад

Спека: `docs/superpowers/specs/2026-08-11-color-ownership.md`.

Порядок выбран так, чтобы каждый шаг был отдельно проверяем и отдельно
откатываем. Виджет идёт раньше дисплея: он меньше, и один его стиль (круг) уже
переведён при починке залипшего ореола — то есть паттерн на нём проверен боем.

## Шаг 0. Характеризация (ДО любой правки кода)

`e2e/color-ownership.spec.js` — снимает **вычисленные** цвет и свечение для
5 стилей × 4 полос в виджете и в дисплее.

Полосы задаются через реальный IPC, пороги берутся из `CONFIG`
(`WARNING_PERCENTAGE: 25`, `DANGER_PERCENTAGE: 10`), а не литералами:

| полоса | как получить |
|---|---|
| normal | total 600, остаток 600 |
| warning | total 100, остаток 20 (≤25%, >10%) |
| danger | total 100, остаток 5 (≤10%) |
| overtime | `allowNegative: true`, остаток −10 |

Тест обязан быть ЗЕЛЁНЫМ до правки — он фиксирует то, что есть. Если он падает
сразу, значит он неверно управляет приложением, и чинить надо тест.

**Критерий готовности шага:** зелёный прогон на неизменённом коде, дважды подряд
(один прогон не отличает стабильный тест от везения).

### Что шаг 0 уже показал

Снимок сделан, тест зелёный дважды. Попутно всплыли **два расхождения между
окнами**. Они существуют ДО правки, к рефакторингу отношения не имеют и потому
**в этот проход не чинятся** — эталон закрепляет их как есть, чтобы правка не
смешалась с изменением внешнего вида:

1. **У виджета аналоговый стиль не показывает полосу `warning`.**
   `widget.analog.warning` = `rgba(255,255,255,0.58)` — ровно то же, что
   `normal`. У дисплея в той же клетке `rgb(255,193,7)`, жёлтый. То есть на
   аналоговых часах виджета предупреждение о четверти оставшегося времени не
   видно вовсе.
2. **Красный у аналога разный в двух окнах.** Виджет —
   `rgba(255,69,58,0.7)` (это `--tw-red` с альфой), дисплей — `rgb(255,68,68)`
   (литерал `#ff4444`). Один и тот же стиль, две разные красноты.

Оба — кандидаты в отдельный проход «свести полосы к одному источнику», который
спека выносит за свои границы, потому что он МЕНЯЕТ пиксели.

Ещё замер оттуда же: 40 клеток дают **9 различных цветов**, среди них три
красных (`#ff4444` ×14, `#ff3333` ×4, `rgba(255,69,58,.7)` ×2) и два жёлтых
(`#ffc107` ×7, `#ffcc00` ×2).

## Шаг 1. Токены полос

В `design-tokens.css` завести производные красного/жёлтого, которыми сейчас
служат литералы:

```
--tw-band-danger  (сейчас #ff4444)
--tw-band-danger-strong (сейчас #ff3333 — LED-вариант)
--tw-band-danger-deep   (сейчас #cc0000 — низ градиента стрелки)
--tw-band-warning (сейчас #ffc107)
```

Значения переносятся ДОСЛОВНО. Сведение их к `--tw-red` — отдельное решение,
меняющее пиксели; в этот проход оно не входит и в спеке вынесено за границы.

**Критерий:** `color-ownership.spec.js` зелёный, значения не изменились.

## Шаг 2. Виджет

Порядок стилей: digital → digits → flip → analog (круг уже сделан).

Для каждого:
1. в CSS — правило `[data-status="…"]` с цветом полосы из токена;
2. в CSS — базовое правило отдаёт цвет переменной `var(--timer-color, …)`;
3. в JS — удалить инлайновый ладдер из `updateDisplay()` /
   `updateFlipDisplay()` / `updateAnalogDisplay()`;
4. прогнать `color-ownership.spec.js`.

Затем: `applyColors()` перестаёт красить и только ставит переменные; поля
`_baseTimerColor` / `_baseDigitalGlow` удаляются вместе с последним читателем.

**Критерий:** ноль `style.color` в `updateDisplay*`; `color-ownership`,
`overtime-palette`, `status-and-colors`, `digits-style` зелёные.

## Шаг 3. Дисплей

То же самое, плюс главный приз: `_enforceOvertimeColors()` удаляется целиком.
Он существует ровно затем, чтобы возвращать инлайн, стёртый другим инлайном —
без инлайна возвращать нечего.

Отдельно проверить `updateProgress()` (5 записей) — там кольцо, у него свой
`strokeDashoffset`, цвет и класс `.danger` могут быть связаны иначе.

**Критерий:** `_enforceOvertimeColors` отсутствует в файле; поля `_base*`
отсутствуют; `color-ownership` и `overtime-palette` зелёные.

## Шаг 4. Сторож

Тест по исходнику: в `updateDisplay*` / `applyColors` трёх окон не должно
появиться новых `style.color =`. Проверить мутацией — вернуть одну запись и
убедиться, что тест краснеет.

Без сторожа паттерн вернётся: он возвращался уже дважды.

## Риски и что с ними

| риск | что делаем |
|---|---|
| у полосы в CSS и в JS РАЗНЫЕ значения → правка меняет пиксели | шаг 0 снимает вычисленные значения; расхождение всплывёт как красный тест, а не как «оно теперь другое» |
| `applyColors` красит то, для чего в CSS правила нет вовсе | тогда правило создаётся на шаге 2/3 с точным текущим значением |
| светлая тема сломает виджет/дисплей | пин палитры не трогаем; переменные ставятся внутри него |
| `visual:check` покажет шум | он недетерминирован (8→0→5→0 на неизменённом main), опорой не служит; при сомнении три прогона на `main` для сравнения |

## Чего в этом проходе НЕ делаем

- часы (полос нет, менять нечего);
- сведение трёх красных к одному (меняет пиксели — отдельное решение);
- разбор `display-script.js` на модули (это соседняя задача, не эта).
