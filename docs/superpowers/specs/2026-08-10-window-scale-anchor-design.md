# Якорь масштабирования виджета и часов — спека

**Дата:** 10 августа 2026
**Слой:** 1 (сервис) — код главного процесса, живущий дольше недели: спека + TDD обязательны
**Статус:** утверждена в брейншторме

---

## Зачем

Жалоба пользователя: «при увеличении масштаба часов и виджета нет возможности
его двинуть наверх».

Формулировка описывает симптом, а не причину, и причина оказалась не там, где её
ищут по тексту жалобы: перетаскивание исправно, сломано масштабирование.

### Замер

Зонд на живом приложении, экран 3440×1440, рабочая область `y = 30…1350`
(сверху строка меню):

| шаг | виджет | часы |
| --- | --- | --- |
| старт | `(3170, 30)` 250×280 | `(3200, 1060)` 220×220 |
| масштаб 400 % | `(3170, 30)` **1000×1000** | `(3200, 1060)` **880×880** |
| тянем вверх −300 | `(3170, **30**)` не сдвинулось | `(3200, 760)` ✓ |
| тянем вверх −600 | `(3170, **30**)` не сдвинулось | `(3200, 160)` ✓ |
| тянем вниз +200 | `(3170, 230)` ✓ | ✓ |
| `setPosition(100, −200)` из главного процесса | приземлилось в `y = **30**` | то же |

`win.setSize()` оставляет неподвижным **левый-верхний угол**, а позицию после
изменения размера не правит никто. Содержимое же отцентрировано в окне
(`.widget-container { justify-content: center }`), поэтому визуальный центр
таймера уезжает вниз-вправо ровно на половину прироста:

- виджет при 400 % занимает `x = 3170…4170` — **730 px за правым краем экрана**,
  центр круга приходится на `x = 3670`, то есть сам циферблат уже вне кадра;
- часы при 400 % занимают `y = 1060…1940` — **500 px ниже нижней кромки**.

Вернуть окно в кадр перетаскиванием можно во все стороны, кроме вверх. Второй
зонд показал, почему, и это важно для границ работы:

| попытка поднять окно выше рабочей области | результат |
| --- | --- |
| `setPosition(1000, 0)` | `y = 30` |
| `setPosition(1000, −100)` | `y = 30` |
| `setBounds({ y: −100 })` | `y = 30` |
| уровень `screen-saver` + `y = −100` | `y = 30` |
| уровень `pop-up-menu` + `y = −100` | `y = 30` |
| `y = 25` (внутрь строки меню) | `y = 30` |

macOS не пускает окно выше рабочей области **ни при каком уровне окна**
(Electron 43.3.0, darwin). Потолок не обходится, и любая попытка его обойти —
потраченное время. Значит чинить надо так, чтобы наверх **не требовалось**
двигать.

## Границы

**Входит:**

- новая чистая функция `fitScaledBounds()` в `window-geometry.js` и её
  юнит-тесты;
- переписанный `resizeWindowClamped()` в `electron-main.js` поверх неё;
- поджатие по рабочей области **того монитора, где окно**, вместо `primary`;
- новый e2e-спек: после масштабирования прямоугольник окна целиком в рабочей
  области, и геометрия переживает переоткрытие;
- попутно — стартовая высота виджета `280` → `250` и подключение
  `WIDGET_DEFAULT_WIDTH` / `WIDGET_DEFAULT_HEIGHT` к конструктору окна
  (сейчас их не читает никто, см. ниже).

**Не входит:**

- новые IPC-каналы — не добавляется ни одного;
- изменения в рендерерах виджета и часов (кроме запасного плана из раздела
  «Открытый вопрос», если замер его потребует);
- новые контролы в панели управления (сетка «прижать к краю» рассмотрена и
  отклонена — см. ниже);
- `positionWindowClamped()`, `moveWindowBy()`, перетаскивание, полноэкранный
  дисплей;
- любые изменения оформления.

## Решения брейншторма

| Вопрос | Решение |
| --- | --- |
| Якорь масштабирования | Центр окна |
| Куда поджимать | В `workArea` дисплея, найденного через `screen.getDisplayMatching()` |
| Где живёт арифметика | Чистая функция в `window-geometry.js`, без Electron внутри |
| Применение | Один `win.setBounds()` вместо `setSize()` |
| Нижняя граница размера | `win.getMinimumSize()`, а не литерал `100` |
| Мусор на входе | Размер по этой оси **не меняется** (запасное значение `220` убирается) |
| Явный орган управления положением | Не добавляется |

Отвергнутые варианты и почему:

- **Сетка 3×3 «прижать к краю» в панели.** Самый заметный вариант, но платит
  новым IPC-каналом в оба whitelist'а, новой разметкой, доступным именем, ARIA,
  контрастом и снимками — за путь восстановления, который исправленное
  масштабирование делает почти ненужным. По истории этого репозитория каждый
  новый канал и контрол — самостоятельный источник дефектов («a whitelisted
  channel is a permission, not a feature»).
- **Стрелки с клавиатуры на виджете и часах.** Дёшевы и не расширяют
  архитектуру (каналы `widget-move` / `clock-widget-move` уже живые), но дают
  точность, а не решают заявленную задачу: вверх выше `y = 30` они тоже не
  пустят. Отложено как отдельная задача эргономики.
- **Обход потолка macOS через уровень окна.** Замерен и не работает — см.
  таблицу выше.

## Как устроено

### `fitScaledBounds()` — чистая функция

```text
fitScaledBounds(current, requested, workArea, min) -> { x, y, width, height }
```

Ни одного обращения к Electron: на вход приходят только прямоугольники, на
выходе — прямоугольник. Поэтому всё содержательное проверяется в Node, без
запуска приложения, как уже устроена остальная геометрия в этом модуле.

Порядок вычисления фиксирован, потому что от него зависят вырожденные случаи:

1. **Размер.** По каждой оси: если запрошенное значение не конечное число или
   не больше нуля — берётся текущий размер окна по этой оси. Иначе
   `clamp(запрошенное, min, workArea)`.
2. **Центр.** `cx = current.x + current.width / 2`, аналогично `cy`.
3. **Позиция.** `x = round(cx − width / 2)`, аналогично `y`.
4. **Поджатие.** `x = max(workArea.x, min(x, workArea.x + workArea.width − width))`,
   аналогично `y`.

Три уточнения, каждое — сознательное решение, а не деталь реализации:

- **Запасное значение `220` убирается.** Сегодня `Number(width) || 220`: ширина
  `0`, `NaN` или `undefined` превращает окно в 220 px независимо от того, каким
  оно было и какое у него базовое значение (у виджета — 250). Станет: испорченное
  значение **игнорируется**, размер по этой оси не меняется. Это тот же принцип,
  который уже записан в `window-geometry.js` про восстановление масштаба —
  «поджать испорченное значение значит молча показать окно неожиданного размера;
  пропустить — оставить прежнее».
- **Нижняя граница берётся из окна** (`win.getMinimumSize()`), а не из литерала
  `100`. У виджета `minWidth: 120`, у часов `120`: посчитав центр по 100, мы
  получили бы от Electron 120 и промахнулись бы мимо центра на 10 px. Литерал
  и настоящий минимум окна — два источника правды, и расходятся они молча.
- **Минимум побеждает рабочую область.** Если окно шире монитора, шаг 4 даёт
  верхнюю границу меньше нижней; порядок `max(lo, min(x, hi))` разрешает это в
  пользу `lo`, то есть окно прижимается к левому-верхнему углу. Случай
  вырожденный, но он обязан быть определён, а не «как получится».

### `resizeWindowClamped()` — главный процесс

Сжимается до чтения границ, поиска дисплея, вызова функции и применения:

```js
const current = win.getBounds();
const [minW, minH] = win.getMinimumSize();
const { workArea } = screen.getDisplayMatching(current);
win.setBounds(WindowGeometry.fitScaledBounds(current, payload, workArea, { width: minW, height: minH }));
```

`setBounds()` вместо `setSize()` — чтобы размер и позиция менялись одним вызовом
и не было промежуточного кадра «уже большое, ещё не сдвинутое».

`screen.getDisplayMatching()` вместо `getPrimaryDisplay()` — на втором мониторе
поджатие по размерам главного экрана неверно уже сегодня, и это та же ошибка,
только другой её край.

Главный процесс начинает `require('./window-geometry.js')`. Модуль уже с двойным
экспортом и уже перечислен в `build.files`; в главном процессе `window`
не определён, ветка браузера не выполнится.

### Что этот подход НЕ ломает и почему

`restore()` в `window-geometry.js` шлёт сначала канал размера, затем канал
позиции. С новым поведением первый вызов **сдвинет** окно (сохраняя центр
текущего положения), второй поставит абсолютную сохранённую позицию. Порядок IPC
сохраняется, поэтому побеждает позиция — восстановление садится ровно туда, где
было.

Но отсюда следует важное: **сравнение `widgetScalePct !== this._geometry.scalePct`
в обработчике `resize` рендерера становится несущим сильнее, чем было.** Раньше
изменение размера не двигало окно, и без этой проверки терялся только масштаб.
Теперь изменение размера двигает окно тоже, и сохранение, случившееся между
двумя посылками восстановления, записало бы промежуточную позицию поверх
восстановленной. Проверка уже стоит и уже прокомментирована как несущая — её
нельзя убирать, и в плане это должно быть отмечено явно.

### Стартовая высота виджета и две мёртвые константы

Виджет создаётся `250×280`, но `WIDGET_BASE_SIZE = 250` в рендерере делает окно
**квадратным** при любом масштабировании: первый же щелчок `Ctrl`+колеса, первое
движение ползунка «Масштаб» и любое восстановление геометрии молча съедают 30 px
высоты. Стартовый вид виджета не воспроизводится больше никогда за всю сессию.

При проверке выяснилось, что в `constants.js` лежат `WIDGET_DEFAULT_WIDTH: 250` и
`WIDGET_DEFAULT_HEIGHT: 280`, которые **не читает ни один файл проекта** —
конструктор окна зашивает те же числа литералами. Это тот же класс гнили, что
проект уже лечил у `CONFIG.STORAGE_KEYS` («реестр, а не точка доступа»): пока у
значения нет единственного владельца, оно расходится молча, и именно это здесь и
произошло.

Поэтому правка не «поменять `280` на `250` в двух местах», а: высота становится
`250`, и конструктор окна начинает **читать** обе константы, получая
единственного владельца. Иначе через полгода литерал и константа разойдутся
снова.

## Открытый вопрос, который решается замером

`setBounds()` вызывает в рендерере и `resize`, и изменение положения. Обработчик
`resize` в виджете и часах вызывает `saveGeometry()`, а тот читает
`window.screenX` / `window.screenY`.

**Успевает ли `screenX` обновиться к моменту, когда до рендерера доходит
`resize`, — неизвестно.** Читать код бесполезно: ответ лежит в порядке
синхронизации визуальных свойств внутри Chromium, а не в нашем коде. Поэтому в
e2e закладывается сценарий «масштаб → закрыть → открыть → позиция совпала», и он
даёт ответ измерением.

**Запасной план, если замер покажет устаревшую позицию:** отложить вызов
`saveGeometry()` в обработчике `resize` на один `requestAnimationFrame`. Это
правка в двух рендерерах, без новых каналов и без изменения контракта. Другие
пути (событие перемещения окна) рендереру недоступны — `move` есть у
`BrowserWindow`, но не у `window`.

### ОТВЕТ (замерено при исполнении)

Гипотеза **опровергнута**: слушатель на `resize` получает
`{outerWidth: 750, screenX: 2690}` — метрики свежие, гонки нет, запасной план
не понадобился.

Замер вскрыл ДРУГОЙ, пре-существующий дефект — в ширине, а не в позиции.
`restore()` выставляет `scalePct` сразу, но окно ещё прежнего размера; раннее
событие `resize` даёт `pct = 100` при `scalePct = 400`, сравнение «не равно»
**пропускает** запись, и восстановленная геометрия затирается позицией открытия
по умолчанию. Окно при этом выглядит правильно, а следующее открытие показывает
размер по умолчанию.

Лечится тем, что решение принимает `window-geometry.js` и принимает его после
тишины в 300 мс, читая `getOuterWidth()` в момент срабатывания, а не в момент
события. Подробности и цифры — в плане реализации.

## Чем доказываем

**Юнит-тесты** (`tests/window-geometry.test.js`), все — на чистой функции:

| случай | ожидание |
| --- | --- |
| рост в середине экрана | центр сохранён |
| уменьшение в середине экрана | центр сохранён |
| окно у правого края растёт | уезжает внутрь, правый край не выходит за рабочую область |
| окно у верхнего края растёт | верх не выходит выше `workArea.y` |
| монитор с ненулевым началом координат (второй экран слева, отрицательный `x`) | поджатие по его собственным границам |
| запрошено больше рабочей области | размер поджат до рабочей области |
| `NaN` / `Infinity` / `0` / `undefined` по одной оси | размер по этой оси не изменился, по другой — применился |
| минимум окна больше рабочей области | прижато к левому-верхнему углу, без инверсии границ |

**e2e** (новый спек), измеряет реальный `BrowserWindow.getBounds()`:

1. Виджет и часы масштабируются до 400 % **тем же каналом, которым это делает
   `Ctrl`+колесо**, — и прямоугольник окна обязан целиком лежать в рабочей
   области своего дисплея. Это ровно то, что сегодня красное: замерено
   `x = 3170…4170` при ширине экрана 3440.
2. Масштаб → закрыть окно → открыть заново → позиция совпала (см. «Открытый
   вопрос»).

**Регрессии, которые надо прогнать не глядя на цвет, а читая вывод:**
`npm run ci`, весь `npx playwright test` (в частности
`e2e/window-drag-geometry.spec.js` — характеризующий тест перетаскивания,
`e2e/clock-badges-layout.spec.js` и `e2e/digits-style.spec.js` — оба меняют
размер окна и теперь будут его двигать) и `npm run visual:check` **трижды
подряд** с нулями.

`CANONICAL_SIZES.widget` в `scripts/screenshot-runner.js` уже `[250, 250]`,
поэтому изменение стартовой высоты виджета не должно тронуть ни одного эталона.
Это предсказание, а не факт, — его проверяет тот же `visual:check`.
